# 正式發布阻擋證據台帳

狀態：`SCOPED_RELEASE_REVIEW_REQUIRED`。本檔是發布前的證據清單，不是發布授權，也不取代法律意見。

發布閘門分成 `public_core`、`account_personalization`、`password_auth`、`reminders` 四個範圍。未指定範圍時會檢查所有已啟用功能並維持 fail-closed；指定範圍時，只採計與該功能真正相關的控制。

指定範圍只決定「檢查哪些條件」，不會自動從網站移除其他功能。真正發布時，部署成品必須已透過設定或獨立建置關閉未選功能；否則不得以較小範圍的結果代表整個成品。

## 已完成但不足以正式發布的事實

- Preview 的程式、CI、兩身分資料庫 RLS 測試與自助刪除介面已完成對應驗證。
- GitHub Pages production、線上 Supabase schema、公告 JSON 與爬蟲均未因 Preview 工作而變更。
- Google OAuth 只驗證登入 UX；RLS 的正式證據以兩個專用 Auth 使用者的一般 JWT 經 Supabase HTTP Data API 驗證為準。

## 分層結果

- `block`：適用功能不得發布，人工確認也不能繞過。
- `review`：需要記錄具體法律或營運判斷；可由發布者明確承擔審查責任，但不得宣稱為法律意見。
- `warning`：允許發布，但必須保留風險紀錄。
- `not_applicable`：該次發布沒有啟用相關功能。

## 防誤報規則

1. CI 綠燈或 Vercel Preview Ready 都不會單獨解除任一阻擋。
2. 不把 Google OAuth 切換帳號測試當成 RLS 證據。
3. 未取得外部證據前，`docs/legal-compliance.json` 的對應技術控制必須保持 `false`；完成後應連同證據更新成 `true`，不得再由程式強迫它永久保持舊值。
4. 不得為解除阻擋而關閉 RLS、放寬來源限制、刪除公告資料或繞過身分核對。
5. `--acknowledge-review` 只能確認人工審查風險，不能略過任何 `block`。

## 法規依據與限制

- 個人資料保護法第 3、5、8、11、19、20 條是帳號資料告知、目的限制、查詢／更正／停止利用／刪除流程的主要檢查依據。
- 著作權法的合理使用必須依具體使用目的、內容性質、利用比例及對市場的影響判斷；「沒有開放授權」本身不自動產生合法或違法結論。
- 閘門只能驗證工程證據與審查紀錄是否存在，不能自行取代法院、主管機關或具資格專業人士的法律判斷。
